# 琉球衝浪基地 Ryukyu Surf Base — 產品規格

版本 0.2｜2026-09-12｜狀態：Phase 1 待 Kaito 驗收；**Phase 1.5 衝浪情報可施工**（模型數據層要等氣象廳確認）；Phase 2/3 待價格與規則確認

## 0. 一句話

讓從台灣、香港飛來沖繩的華語旅客，能在網站上看懂 Kaito 在賣什麼、相信他、然後直接送出預約——而不是只能在 IG 私訊。

## 1. 背景

Kaito（海斗）是沖繩出生長大的衝浪教練，2025-08-19 開設「琉球衝浪基地」，高中畢業後在台灣留學一年半，中文可溝通。曾罹患憂鬱症、離職，靠「死之前還想再衝一次浪」的念頭重新回到海裡，開業初衷是「透過大海與衝浪，幫助同樣背負壓力的人」。

目前所有客源都在 IG（769 粉絲），預約靠私訊。回頭客比例高。

**這個故事是網站最強的資產，但要克制地講**：放在獨立的「關於教練」頁完整說，首頁只給一到兩句引子。不要把憂鬱症當行銷賣點鋪滿全站。

## 2. 目標與非目標

**目標**
- 一個有品牌感、看得出「他真的懂沖繩的海」的官網
- 衝浪情報：教旅客自己看懂沖繩的浪，提供看浪用的數據，並用 Telegram 頻道每天推送（Phase 1.5）
- 訪客能自助送出預約申請（Phase 2）
- 預約自動落進 Kaito 的 Google Calendar，他不必再手動記
- 他能自己改內容、看預約，不必找 SS（Phase 3）

**非目標（明確不做）**
- 線上付款 — 短期一律現場收款
- IG feed 自動同步牆
- 會員系統、登入、多教練排班
- SEO 內容農場（2026-09-12 SS 改為要做簡單 Blog，由 Kaito 自己寫，見 `docs/ADMIN_SPEC.md`）
- 電商賣板／賣周邊
- **自己推算的浪況判斷、評分、推薦時段** — 受氣象業務法規範，見 §6.1

## 5. 視覺與動效

- **色**（2026-09-11 SS 改定，取代原本的深海藍底）：**淺色為預設**，調性是開心、活潑、健康、沖繩海島。白沙 `#fff8ec` 為底，沖繩淺灘青綠 `#2cc5b4` 為主色，扶桑花珊瑚 `#ff7657` 只給主按鈕，紅瓦色 `#c2462c` 用在編號點綴，文字用 logo 的深藍 `#12394a`。整頁只留 footer 一塊深色收尾。小字一律用深色版本（`--lagoon-ink` / `--coral-ink`），亮色只給大面積色塊，確保對比 ≥ 4.5。仍然避開一般潛水站愛用的飽和天藍。token 定義在 `src/styles.css` 的 `:root`。舊的深色版本在 commit `b3d2d3b`
- **字**：繁中 Noto Sans TC，日文 Noto Sans JP，數字/英文用一套 grotesque。標題重、內文輕，對比要拉開
- **標題日文小字**（2026-09-12 定案）：每個頁面 H1、區塊 H2 上方的 eyebrow 小字顯示另一種語言。繁中頁面顯示日文（例如「サーフ情報」），日文頁面顯示繁中。方案名稱這類小標題也一樣，兩種語言寫法相同時（例如 Surf Trip）就不重複。英文不當小字，只放在專業用詞旁的括號裡。中文標題排版底線照舊（line-height ≥ 1.05、letter-spacing ≥ -0.01em）
- **海浪動畫**：Canvas 疊 2–3 層 sine 波，低振幅慢速；hero 之外的區塊分隔用靜態 SVG 波浪。手機降到 2 層。`prefers-reduced-motion: reduce` 時完全靜止
- **海浪聲**：單一 20–30 秒無縫 loop mp3（< 400KB），Web Audio API，開啟時 1.5 秒淡入。**預設靜音**，開關固定在右下，狀態存 localStorage。頁面切到背景時自動暫停
- **照片**：橫幅用 Kaito 原檔，WebP + 尺寸切三段。**Phase 1 用 placeholder，不得使用 `_scraped/` 裡的 IG 壓縮圖上線**

## 6. 衝浪情報 Surf Report（Phase 1.5）

### 6.1 定位與法規紅線（違反即為錯誤）

**定位：教人自己看懂沖繩的浪，並提供看浪用的數據。網站不替使用者下結論。**

依據是気象業務法第 17 條：對日本國內使用者提供自己推算的波浪預報，必須取得氣象廳許可。另外，只解說氣象廳或許可業者的預報，不需要許可。查證記錄與來源在 `docs/FORECAST_IDEA.md`。

**允許**
- 轉載氣象廳預報、警報注意報的原文（可以翻譯，但要註明出處，也要註明有翻譯或加工）
- 潮位表、日出日落等數據原樣呈現
- 通則性的解說與教學（例如「東風對面西的海岸是離岸風」）
- 浪點的靜態介紹（由 Kaito 提供）
- 現況觀察（Kaito 的現場報告）

**禁止**（網站、Telegram、og 描述、SEO 文字全部適用）
- 對未來的時段輸出「適合／不適合／建議／推薦／おすすめ／recommended」、分數、星等、紅黃綠燈號
- 自動把當天數據拿去跟浪點條件比對，標出「今天 X 浪點符合條件」
- 對模型數據做內插或地形修正後，當成某個浪點的數值

### 6.2 資料來源

| 資料 | 來源 | 範圍 | 更新 | 呈現方式 |
|---|---|---|---|---|
| 潮汐（每小時潮位＋滿潮／乾潮） | 氣象廳潮位表文字檔 `https://www.data.jma.go.jp/kaiyou/data/db/tide/suisan/txt/{YYYY}/{站碼}.txt`。西岸用那霸 `NH`，東岸用沖繩（中城湾港）`ZO` | 整年（至少顯示 7 天） | 年檔，快取 | 原樣；註明出處，並註明「依氣象廳潮位表繪製」 |
| 日出日落 | 用天文公式計算（那霸座標），不接外部 API | 不限 | — | 原樣 |
| 天氣、風、浪（文字） | 氣象廳 `https://www.jma.go.jp/bosai/forecast/data/forecast/471000.json` 第 0 區塊，分本島中南部 `471010` 與本島北部 `471020` | **3 天** | 05／11／17 時發布 | 日文原文＋翻譯，註明出處 |
| 週間天氣、降雨機率、氣溫、信賴度 | 同一個 JSON 的第 1 區塊（`471000`、那霸 `91197`） | **7 天** | 11／17 時 | 原樣＋翻譯。**週間預報不含浪與風**，頁面要寫明 |
| 警報、注意報 | 氣象廳 `https://www.jma.go.jp/bosai/warning/data/warning/471000.json` | 當下 | 有發布時才更新 | 原文＋翻譯。2026-09-12 抓到的 `reportDatetime` 還停在 2026-05-28，實作時要先驗證這個 endpoint 還有沒有在更新 |
| 逐時湧浪高度／方向／週期、逐時風與陣風 | Open-Meteo Marine API ＋ Forecast API（**必須是商用付費方案**） | 7 天 | 每 3 小時左右 | **模型數據層，預設關閉**（見下方） |

**模型數據層**：功能開關 `MODEL_LAYER_ENABLED` 預設為 `false`。要同時滿足以下兩點，SS 才會打開：
- (a) 向氣象廳確認這種呈現方式不算預報業務（諮詢稿見 `docs/JMA_INQUIRY.md`）
- (b) 已購買 Open-Meteo 商用方案

打開之後，每個海岸只放一個代表點，數值原樣呈現、不做內插，並附上「這是數值模型的計算結果，不是預報，可能有很大誤差」。開關關閉期間，每個海岸改放 Windy 的外部連結。

**暫不做**：NOWPHAS 即時浪高觀測。沖繩的站點與轉載條件都還沒確認。

### 6.3 頁面

**`/surf-report` 衝浪情報**
- 7 個日期分頁（今天到第 6 天），網址帶 `?date=YYYY-MM-DD`，TG 的連結直接開到那一天
- 每天依序顯示以下區塊，沒有資料的區塊整塊不顯示：
  1. 警報、注意報（有發布才顯示，放最上面）
  2. 潮汐：西岸（那霸）、東岸（中城湾港）兩條潮位曲線，並標出滿潮與乾潮的時間和潮位（cm，以潮位表基準面為準）
  3. 日出、日落
  4. 氣象廳預報：第 0–2 天有天氣、風、浪；第 3–6 天只有天氣、降雨機率、氣溫、信賴度，並寫明「第 3 天以後氣象廳不發布浪與風」
  5. 模型數據表（開關打開才顯示）
  6. Kaito 現場報告（只在今天、而且有發文時顯示，附發文時間）
- 每個區塊都附「怎麼看 →」連結，連到 `/surf-guide` 對應的段落
- 每個來源都顯示最後更新時間。抓取失敗時顯示上一次成功的資料與時間，不可以顯示空白
- 頁尾放出處與免責聲明

**`/surf-guide` 怎麼看浪**
- 八個步驟：潮汐 → 湧浪高度 → 湧浪方向 → 週期 → 風向 → 風速與陣風 → 浪點朝向 → 自己的程度
- 每一步寫三件事：要看哪個數字、這個數字在沖繩代表什麼、常見誤會（例如「海面很平很漂亮」不等於「有浪可以衝」）
- 放一張沖繩本島四面海岸的 SVG 示意圖，標出各海岸吃哪個方向的湧浪、哪個方向的風是離岸風。這張圖是通則，不連動當天數據
- 結尾寫明：沒有浪、有颱風、發布高浪注意報的日子，就是休息日
- 文案初稿由 Claude 撰寫，Kaito 看過才能上線

**`/surf-points` 沖繩四面海岸**（2026-09-12 SS 定案：只留通則）
- 分成西、東、南、北四面海岸，每面只寫面向、收到的湧浪方向、離岸風方向這類通則
- **不列出具體浪點**：Kaito 的在地規則是不以任何形式公開衝浪點資訊，網站也照做，並在頁面上註明
- 內容**不得**連動當天數據（§6.1）

### 6.4 Telegram 推播

- Bot `@Ryukyusurf_bot`（SS 已於 2026-09-12 建立）。發到公開頻道（單向廣播），bot 要設成頻道管理員。頻道名稱與擁有者待定
- **今天的報告**：每天 05:15 JST，靜音發送（`disable_notification: true`）
- **明天的報告**：每天 11:15 JST
- 內容：日期、日出日落、西岸與東岸的滿潮乾潮、氣象廳的天氣／風／浪（日文原文＋翻譯）、警報注意報，以及連到 `/surf-report?date=YYYY-MM-DD` 的連結。內容以繁中為主、標題附日文，天氣／風／浪附日文原文，數字不翻譯
- 內容不得出現 §6.1 禁止的判斷字眼
- **Kaito 現場報告**：Kaito 在頻道發一則以 `#現場` 開頭的貼文 → bot 透過 webhook 收到 `channel_post` → 存進 D1 → 網站今天的頁面顯示出來。**這項要 Kaito 同意才上線**
- Token：本機放 `~/.config/ryukyusurfbase/telegram.json`，雲端用 `wrangler secret put`。**絕不進 repo，也不要貼進對話**

### 6.5 技術

- Worker 放在 repo 的 `worker/`，名稱 `ryukyusurfbase-api`
- Cron Triggers（以 UTC 撰寫）：
  - `10 20,2,8 * * *`：抓氣象廳預報與警報（JST 05:10／11:10／17:10）
  - `15 20 * * *`：發今天的報告（JST 05:15）
  - `15 2 * * *`：發明天的報告（JST 11:15）
  - `0 21 * * 1`：每週一補抓今年與明年的潮位表年檔（明年的檔案可能還沒發布，抓不到時略過）
- 發報前先檢查氣象廳 JSON 的 `reportDatetime`。如果不是最新那一版，重抓一次；還是舊的就照發，並在訊息中寫出「氣象廳資料時間：…」
- D1 資料表：
  - `jma_forecasts(report_datetime, office, payload_json, fetched_at)`
  - `jma_warnings(report_datetime, payload_json, fetched_at)`
  - `tides(station, date, hourly_json, highs_json, lows_json)`
  - `field_reports(id, posted_at, text, tg_message_id)`
  - `tg_posts(kind, target_date, message_id, sent_at, status)`
- API：`GET /api/surf-report?from=YYYY-MM-DD&days=7`，一次回傳整週資料。CORS 只允許預覽站與正式網域
- 所有日期時間一律以 JST 處理

## 7. 預約系統（Phase 2）

> **2026-09-12 SS 決定自建預約系統**，不只用 Google 表單。已經先做了前端示範：客人端 `/booking`、Kaito 端 `/booking/demo-admin`。示範版的資料只存在瀏覽器，日期狀態是假資料，不放進主選單。流程與欄位依 Kaito 現行的 Google 預約表單調整，下面的規格已同步更新。

### 流程
1. 訪客選方案 → 選日期（日曆只顯示未來 60 天）
2. 前端呼叫 `GET /api/availability?from=&to=` → Worker 用 Service Account 讀 Kaito 日曆 freebusy → 回傳每日狀態（可約／已滿／不開放）
3. 填表（依 Kaito 的 Google 表單）：姓名、拼音（選填）、電話、email、人數、衝浪經驗（第一次／初學者／中級者／進階者）、防寒衣租借件數與身高體重、硬板租借片數（只限衝浪導覽）、備註（不會游泳、受傷經歷、疾病）、得知管道（選填）
4. 確認頁顯示預估費用（依收費方案試算，當日現金支付），並勾選三項同意：取消政策、參加須知、在地規則，三項都勾才能送出
5. 送出 → `POST /api/bookings` → 寫 D1，狀態 `pending`
6. Worker 在 Kaito 日曆建立 **tentative** 事件，標題 `[待確認] 方案 / 姓名 / 人數`
7. 通知 Kaito（Phase 2 先用 email；LINE Notify 已停止服務，若要 IM 推播走 Telegram Bot）
8. Kaito 在後台或直接回覆確認 → 狀態轉 `confirmed`，日曆事件轉 confirmed

## 最重要的一條

**§6.1 法規紅線**：網站、Telegram、og 描述、SEO 文字，一律不得出現對未來時段的判斷，包括「適合／不適合／建議／推薦／おすすめ／recommended」、分數、星等、紅黃綠燈號，也不得自動拿數據去比對浪點條件。只做「原樣呈現數據＋通則解說」。

這不是風格偏好，是氣象業務法的問題。不確定某段文字算不算判斷時，先寫進回報交給 SS 決定，不要自己判斷後放上去。

- `/about` 故事的英文譯稿先放進去，但加上 `// TODO: Kaito 審閱` 註解

### 2. Worker 骨架與潮位表
- `worker/`：wrangler 專案、D1 schema（SPEC §6.5）、本機用 `wrangler dev`
- 潮位表解析，格式規則如下：
  - 每一行是一天
  - 第 1–72 字元：每小時潮位，3 個字元 × 24 小時
  - 第 73–78 字元：日期，年、月、日各 2 字元，**會用空白補位**
  - 第 79–80 字元：站碼
  - 第 81–108 字元：滿潮，4 組 × 7 字元（時刻 4 字元＋潮位 3 字元）
  - 第 109–136 字元：乾潮，4 組 × 7 字元
  - **時刻 4 字元是「時 2 字元＋分 2 字元」，兩者都可能用空白補位**。例如 ` 2 8` 代表 02:08，` 817` 代表 08:17
  - 沒有資料的欄位是 `9999` 與 `999`
- **單元測試必須包含 2026-09-13 的實際值**：
  - NH：滿潮 08:17 222cm、20:23 221cm；乾潮 02:08 46cm、14:22 52cm
  - ZO：滿潮 07:50 222cm、19:57 221cm；乾潮 01:39 53cm、13:53 57cm
- 日出日落用天文公式計算（那霸座標），寫單元測試，誤差要在 ±2 分鐘內

### 3. 氣象廳預報與警報
- 解析 `471000.json`：第 0 區塊（3 天的天氣、風、浪，分 471010 與 471020 兩區）、第 1 區塊（7 天的週間天氣）
- 翻譯氣象廳的固定片語（例如「東の風　後　北東の風」「うねり　を伴う」），用一張對照表處理。對照表裡查不到的片語就保留日文原文，不要猜
- 警報 endpoint `warning/471000.json`：先驗證還有沒有在更新（2026-09-12 抓到的 reportDatetime 還停在 2026-05-28），把驗證結果寫進回報。警報代碼要對照氣象廳公開的代碼表，不要猜
- 保存每次抓取的原始 JSON。抓取失敗時沿用上一次成功的資料

### 4. `/surf-report` 頁
依 SPEC §6.3 做。7 個日期分頁，網址帶 `?date=`。沒有資料的區塊整塊不顯示。每個來源都要顯示更新時間，頁尾放出處與免責聲明（三語）。模型數據層先做好元件，但受 `MODEL_LAYER_ENABLED` 控制，預設關閉；關閉時每個海岸改放 Windy 外部連結。

### 7. Telegram
- 依 SPEC §6.4 產生今天與明天的報告訊息，並用 cron 發送
- 用 webhook 收 `channel_post`：只收 `#現場` 開頭的貼文，存進 `field_reports`
- Token 一律從 `env` 讀取。**不得寫進任何檔案、測試或範例**。範例設定只能用 `TELEGRAM_BOT_TOKEN=` 空值

### 8. 防呆腳本
新增 `npm run check:forecast-words`，掃描 i18n 字典、Worker 的訊息模板和頁面文案。發現以下字眼就讓指令失敗：`適合|不適合|建議|推薦|おすすめ|オススメ|recommend|rating|score|⭐|★`。

教學頁需要說明「怎麼判斷適不適合自己的程度」時，一定會用到其中某些字，所以允許清單**要逐字列出，並附上理由**。
